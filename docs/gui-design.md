# GUI 設計：状況管理

**状態: 設計のみ。実装はまだない。** 実装に入る前に、末尾の「決めたいこと」を確認する。

## 目的

このプロジェクトは「資産を増やす目標を達成する確率」を上げるための検証環境である。
GUI の仕事は、**今どこまで進んでいて、次に何をすべきか、やってはいけないことは何か**を
一目で分かるようにすること。計算や判断のロジックは GUI に持たせない。

管理したい「状況」は4種類ある。

| 種類 | 知りたいこと |
|---|---|
| データ | どの期間が取れているか、欠けはないか、取得は今どこまで進んでいるか |
| 研究 | 何を何回試したか、ベースライン（買い持ち・ランダム）に勝ったか |
| 前向き検証（実運用） | 1万円で動かした結果が、バックテストの想定とどれだけずれたか |
| 目標・リスク | 月次で目標に近づいているか、許容する下落を超えていないか |

## 位置づけ（訂正）

このGUIは、**検証のための道具ではなく、実運用の操作盤**として設計する。
稼働中の売買システムを安全に見守り、必要なときに止めたり設定を変えたりするためのもの。

- 実運用で問うのは「今、正常に動いているか」「いくら持っていて損益はいくらか」
  「おかしな注文が出ていないか、出たらどう止めるか」
- 日足の戦略なら動きは「引け後に判断 → 翌朝の寄りで発注」の1日1回。画面に張りつくものではなく、
  **朝と夕方に確認するもの**になる。画面を開かなくても気づけるよう、**異常の通知**を重視する
- 下の「画面」のうち、**研究**（実験の比較、試行回数、ロックボックス）は検証の仕事なので、
  操作盤の対象から外し、レポートか別画面に分ける。**前向き検証**の画面が、実運用の中核になる
- 操作盤が必要になるのは、運用に載せられる戦略が見つかってから。作る順番は、検証の後でよい

## 配備（ローカルから始める）

**当面はローカル（このMac）で動かす。** スマホからの利用や常時稼働が必要になったら、
クラウド（GCP の仮想マシン1台）へ移す。移行の時期は、実発注（モード3）に入る時点を目安にする。

ローカルでも、**あとで移せる作り**だけは守る。

| 守ること | 理由 |
|---|---|
| 設定は環境変数で渡す。コードに埋め込まない | 環境ごとに値を替えるだけで動かすため |
| 状態の保存は `StateStore`（Port）経由。SQLite は実装の一つ | 保存先を替えても、呼ぶ側が変わらないため |
| 認証情報は `.env` から読む層を1か所にまとめる | クラウドでは Secret Manager に差し替えるため |
| Dockerfile で環境を固める（実運用に近づいたら） | 動く環境を再現できるようにするため |
| GUI は Web アプリとして作り、既定は `127.0.0.1` | そのまま閉じた経路でも公開できる |
| 通知は `Notifier`（Port）経由 | 届け先（メール、Slack など）を後から決められる |

クラウドに移す場合の前提（今は実施しない）:

- 公開ポートを開けない。Identity-Aware Proxy か Tailscale のような閉じた経路を通す
- 認証情報は Secret Manager に置く。予算アラートを必ず設定する
- キルスイッチは、操作盤とは別の経路で止められるようにする
- 証券会社のAPIが、クラウド上で動くかを先に確認する
  （自分のPCでアプリを起動しておく必要があるAPIは、クラウドだけでは完結しない）

## 設計の原則

1. **GUI は shell。ロジックは書かない。** FCIS（Functional Core, Imperative Shell）に従い、
   GUI は `interfaces` 層に置く。計算は `core` / `application` の関数を呼ぶだけにする。
   画面に出す値の整形は、純粋関数の **view-model** に分け、GUI なしでテストできるようにする。
2. **発注は段階を踏んで解禁する。** 最初は注文を出さない（約定は手入力）。自動売買は
   「実行モード」を一段ずつ上げる設計にし、**条件を満たすまで次のモードに進めない**
   （後述「売買と自動売買の設定」）。表示するシグナルは検証ツールの出力であり、投資助言ではない。
3. **APIキーは画面に出さない。** 「設定済み / 未設定」だけを表示する。キーは `.env` にのみ置く。
4. **研究の履歴は追記のみ。** 試した回数が多重検定の補正（`core/selection.py`）の入力になる。
   後から消せる・書き換えられると、「何回試したか」が嘘になる。
5. **当面はローカル専用。** 既定は `127.0.0.1` で待ち受ける。外部公開する場合は認証を別途設計する
   （「配備」を参照）。

## 全体構成

```
interfaces/
  gui/              ← 新規。画面（薄い）
  viewmodels/       ← 新規。純粋関数。表示用の値を作る
application/
  ports.py          ← 追加: ExperimentRepository, LedgerRepository, JobRunner
  jobs.py           ← 新規: 取得・バックテストをジョブとして実行し、進捗をイベントで返す
infrastructure/
  sqlite_state.py   ← 新規: 状態の保存（標準ライブラリの sqlite3）
  jquants.py / parquet_store.py（既存）
state/              ← gitignore。jqbt.db（状態）、logs/
data/               ← 既存。相場データ（Parquet）
```

依存方向は既存の `tests/test_architecture.py` に従う。**`core` は GUI を知らない。**
`interfaces/gui` から `application` と `infrastructure` を呼んでよい。

### 状態の保存

相場データは Parquet のまま。**状態（実験・ジョブ・実運用の記録）は SQLite 1ファイル**に置く。
標準ライブラリだけで動き、バックアップはファイルのコピーで済む。

| テーブル | 内容 | 変更 |
|---|---|---|
| `experiments` | 戦略、パラメータ、期間、売買単位、コスト前提、コミットID、結果の要約 | 追記のみ |
| `trials` | 1回の試行（最適化で試した組み合わせ）。多重検定の N を数える | 追記のみ |
| `jobs` | 種別（fetch / backtest / validate）、状態、開始・終了、ログの場所 | 更新可 |
| `signals` | 日付、銘柄、売買、想定数量、根拠。凍結した戦略が出したもの | 追記のみ |
| `fills_actual` | 手入力した実際の約定（日時、価格、数量、手数料、メモ） | 追記（訂正は別行） |
| `equity_snapshots` | 日次の評価額（実運用）と、同期間のバックテストの想定値 | 追記のみ |
| `assumptions` | コスト前提（追加スプレッドなど）と **出所**（仮定 / 実測） | 追記のみ |

### ジョブと進捗

取得やバックテストは数十分〜数時間かかる。GUI を固まらせないため、**別プロセスのジョブ**にする。

- ジョブは進捗を **JSON Lines のイベント**で書き出す（例: `{"job": 12, "done": 120, "total": 290, "eta_min": 84}`）。
  いま `scripts/fetch.py` が出している `[処理済み/対象] 日付 経過 / 残り` の行を、同じ内容の構造化イベントにする。
- GUI はイベントファイルを読むだけ。ジョブの中身を知らない。
- 停止はシグナル（SIGTERM）で行う。取得は再開可能なので、止めても失われない。
- Mac のスリープで経過時間がずれる点に注意（壁時計ではなく処理時間で ETA を出す）。

## 画面

### 1. 今日（ダッシュボード）
- データの鮮度（最新の取得日、欠けの有無）、実行中のジョブ、アラート
- 前向き検証の評価額と、バックテストの想定との差
- 「次にやること」: 例）今日のシグナルが未確認 / 約定の入力待ち / 増額条件の達成状況

### 2. データ
- 取得済みカレンダー（営業日 / 休場 / 未取得 / 欠け）
- 取得の開始・停止、ETA、429 や再試行の回数、レート制限の余裕の設定
- プラン（Free は12週間遅延）と、使える期間

### 3. 研究
- 実験の一覧と比較（戦略、売買単位、コスト前提別）。**買い持ち・ランダムの分布を常に並べる**
- **試行回数カウンタ**: 何通り試したか、「何もなくてもこの程度は出る」水準（期待最大 Sharpe）との比較
- **最後の検証用期間（ロックボックス）**: 未使用 / 使用済みを表示し、**一度見たら記録する**。見た後の変更は検証のやり直し扱い
- 警告の集約（取引数不足、t値、コスト負け、窓の数不足）

### 4. 前向き検証（実運用）
- **シグナル表**: 凍結した戦略が出した、明日の売買候補
- **約定入力フォーム**: 実際の価格・数量・手数料。シグナルとの紐づけ
- **想定とのずれ**: 約定価格 − 想定価格（スリッページ）の分布。想定のスプレッドが妥当かの判定
- 評価額の推移、月次損益、最大ドローダウン
- **戦略の凍結**: コミットIDとパラメータのハッシュを記録。変更したら新しい検証として扱う

### 5. 目標とリスク
- 月次の物差し: 月次リターン、元本割れ月の割合、目標達成確率（ローリング）
- 許容ドローダウンと、超えたときの停止ルール（人が判断するための表示）
- **増額条件のチェックリスト**（例: 3か月継続 / 実際のスリッページが想定内 / DD が許容内）。全部満たすまで次の段階に進めない

### 6. 設定
- 証券会社プロファイル（売買単位、手数料、追加スプレッド、**仮定か実測か**）
- 銘柄種別の選択（株 / 将来 FX）

## FX など他の手段への拡張

画面は **Instrument（銘柄仕様）** を介して作る。株を前提にした表示を直接書かない。

- 売買単位、価格の刻み、取引時間は Instrument から取る
- 建玉の表示は、買い・売りの両方と証拠金（維持率）を扱える形にしておく
- 研究・前向き検証の画面は、Instrument ごとに切り替える

`core` 側に `Instrument` が入るまでは、GUI も株専用で作る。**先回りして汎用化しない。**
ただし、画面が `lot_size = 100` のような値を直接持たないようにだけ守る。

## 段階（実装する場合）

| 段階 | 内容 | GUI の要否 |
|---|---|---|
| P0 | ジョブの進捗イベント化、SQLite の状態保存、実験の自動記録（CLI から） | なし（GUI なしでも有用） |
| P1 | 読み取り専用の画面（今日・データ・研究） | 要 |
| P2 | 前向き検証（シグナル表、約定入力、ずれの表示、増額条件） | 要 |
| P3 | ジョブの操作（取得の開始・停止、バックテストの実行） | 要 |
| P4 | Instrument の導入に合わせた FX 対応 | 要 |
| P5 | 設定の変更（戦略の版管理、リスク制限、実行モード）と監査ログ | 要 |
| P6 | ペーパー発注（モード2）。`BrokerPort` とペーパーアダプター | 要 |
| P7 | 実発注（モード3→4）。**P5・P6 とキルスイッチが前提** | 要 |

P0 は GUI が決まらなくても着手できる。**研究の履歴を最初から残しておかないと、
試行回数が数えられなくなる**ため、実は最優先である。

## 技術の選択肢

| 案 | 長所 | 短所 |
|---|---|---|
| Streamlit | Python だけで速く作れる。表とグラフに強い | 再実行モデルで、長いジョブの扱いに工夫が要る |
| NiceGUI | 非同期・バックグラウンド処理が素直 | 採用例が少ない |
| FastAPI + 軽いフロント | 分離が明確。将来のスマホ対応にも向く | 作る量が多い |

**推奨は Streamlit で P1〜P2 を作ること。** ジョブは別プロセスにして、Streamlit は
状態の読み取りと表示に徹する。view-model を分けておけば、後から差し替えられる。

## 決めたいこと

1. **使う場所**: このMacのみか。スマホから見たいか（外部公開は認証の設計が増える）
2. **最初に欲しい画面**: 優先順位（推奨は 研究の履歴 → 前向き検証 → データ）
3. **技術**: 推奨の Streamlit でよいか
4. **増額条件の中身**: 継続期間、許容ドローダウン、スリッページの許容幅
5. **使う証券会社と、そのAPIの有無**（単元未満株・FX の対応を含む）
6. **自動売買の最終形**: 人の承認付き（モード3）で十分か、完全自動（モード4）まで欲しいか

## 売買と自動売買の設定

GUI から売買に関わる設定を変えられるようにする。**資金が動く設定を画面から変えられる**ということなので、
設定を3種類に分け、変えやすさと安全装置を変える。

### 設定の種類

| 種類 | 例 | 変更のルール |
|---|---|---|
| 研究用 | 検証の期間、コスト前提、候補のパラメータ | 自由に変えてよい。実験として記録される |
| 戦略（実運用プロファイル） | 戦略の種類、パラメータ、銘柄の条件 | **変更は新しいバージョン**になる。差分を表示し、確認を経て、**翌営業日から有効**。前向き検証は仕切り直し |
| リスク制限 | 1注文の上限額、1銘柄の上限、1日の損失上限、最大ポジション数 | **厳しくする変更は即時**。緩める変更は確認と待機時間（例: 24時間）を置く |

### 実行モード

| モード | 動作 | 次に進む条件（例） |
|---|---|---|
| 0 停止 | 何もしない | — |
| 1 シグナルのみ | 売買候補を表示する。発注は人が行い、約定は手入力 | — |
| 2 ペーパー | 仮想の約定で、実運用と同じ流れを回す（バックテストと同じ約定ロジックを使う） | 一定期間、エラーなく継続 |
| 3 確認付き実発注 | 注文案を作り、**人が承認したものだけ**を発注する | ペーパーで想定どおり。リスク制限を設定済み |
| 4 自動発注 | 制限の範囲内で、承認なしで発注する | 確認付きで一定期間、想定とのずれが許容内 |

**モードを上げるのは、チェックリストを満たしたときだけ。下げるのは、いつでも即時。**

### 安全装置（自動売買の前提）

- **キルスイッチ**: GUI とは別プロセスで監視し、GUI が固まっていても止まる。ファイルフラグで即時停止できる
- **発注前の検査**: 1注文の上限額、基準価格からの乖離（異常な価格での発注の拒否）、重複発注の防止（注文IDの冪等性）、取引時間内かの確認
- **日次の損失上限**: 超えたら、その日はモード1に自動で落ちる
- **照合（リコンサイル）**: 証券会社の保有・残高と、システムの記録を定期的に突き合わせ、ずれたら停止
- **監査ログ**: 設定の変更はすべて追記のみで記録する（誰が・いつ・何を・旧値・新値・理由）。後から消せない
- **認証情報**: 証券会社のキーは OS のキーチェーンか `.env` にだけ置く。GUI には表示せず、変更も画面からはしない

### 構成（FCIS）

- 判断（戦略 → 注文案）は純粋関数のまま。バックテストと実運用で**同じコード**を使う
- 発注は shell の仕事。`application/ports.py` に `BrokerPort` を置き、証券会社ごとのアダプターを `infrastructure` に置く
- 最初に作るアダプターは **ペーパー**（`core/execution.py` の約定ロジックを再利用）。実運用の証券会社は、その後

### 先に確認が要ること

- **証券会社のAPIが使えるか**。個人向けに公開されているAPIは限られ、**単元未満株に対応していないものが多い**（要確認）。
  1万円・1株単位という前提と、自動発注が両立しない可能性がある。両立しない場合は、
  モード3（人が承認して手動発注）までを自動化の上限にし、実発注は人が行う運用になる
- **自分の口座で個人として使う範囲に留める**。他人の資産を運用したり、第三者に提供したりすると、
  金融商品取引法上の登録が必要になる場合がある

## 非目標

- 複数ユーザー、権限管理
- 売買の推奨（投資助言）
- 他人の資金の運用、第三者への提供
