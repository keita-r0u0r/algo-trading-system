# jqbt — 国内株のバックテスト環境（研究用）

自動売買システムそのものではありません。**その手前の、検証環境だけ**です。

目的は1つ。

> ある銘柄・ある期間について、売買ルールを与えると、手数料・スリッページ込みで
> 取引履歴・損益・最大ドローダウン・Sharpe 等を **再現可能な形で** 算出する

ここが信用できないまま先に進むと、あとの全部が無意味になります。

---

## すぐ動かす

```bash
pip install -e ".[dev]"

# 合成データ（認証不要・成績に意味はない・仕組みの確認用）
python scripts/run.py --compare --synthetic

# 実データ
cp .env.example .env     # JQUANTS_API_KEY に発行したキーを書く
python scripts/fetch.py --years 2
python scripts/run.py --strategy sma_cross --start 2023-01-01 --end 2024-12-31

# Out-of-Sample 検証（★戦略を信じる前にこれ）
python scripts/validate.py walkforward --strategy sma_cross --synthetic --train 250 --test 120

pytest
```

## 先に知っておくべき3つの数字

### 1. 利益目標と必要利回り

税引後10万円の利益を出すには、税引前で **125,494円** 必要です（申告分離課税 20.315%）。

| 元本 | 必要年率 |
|---|---|
| 10万円 | 125.5% |
| 30万円 | **41.8%** |
| 100万円 | 12.5% |
| 300万円 | 4.2% |

30万円で年10万円は、**年率41.8%を継続する**ということです。これは一流のヘッジファンドが
達成できていない水準です。年50万円なら30万円の元本に対して209%。

目標の立て方を変える必要があります。選択肢は3つです。

- 現実的な利回り（10〜15%）を受け入れて、**利益額を下げる**（30万円 → 年3〜4.5万円）
- **元本を増やす**（年率15%で税引後10万円なら約84万円、50万円なら約420万円）
- 金額目標を降ろして、**学習目的に振り切る**

どれを選んでも構いませんが、41.8%を前提に戦略を探すと、
「バックテストで41.8%出た戦略」＝過学習したもの、を選んでしまいます。

### 2. 単元株の壁

国内株は100株単位です。資金30万円を3銘柄に分けると1銘柄10万円、
つまり **株価1,000円を超える銘柄は1単元も買えません**。

`scripts/run.py` は毎回これを表示します。

```
【資金と単元株の制約】
  1銘柄あたり予算      100,000円（300,000円 ÷ 3銘柄）
  買える株価の上限      1,000円（単元100株のため）
  買える銘柄            5 / 30（17%）
  ! 母集団の83%は資金不足で買えません。
    検証結果は実質的に低位株のみのものになり、市場全体の性質とは異なります。
```

これは制約であると同時に **バイアス** です。低位株はボラティリティ・流動性・
業種構成が市場平均と違うため、全銘柄で検証した結果をそのまま適用できません。

対処としては、**2通り回す**のが正解です。

- 研究モード（`--ignore-lot-size`、資金を大きく）→ 「そもそも優位性があるか」
- 実装モード（実際の資金・単元株あり）→ 「その優位性を取れるか」

この2つの差が、実際に手に入る分です。

### 3. コストの支配力

株価1,000円の銘柄の呼値は1円。最良気配を取りに行くだけで往復0.2%。
年10回転させれば年2%がスプレッドだけで消えます。手数料が無料でもです。

`--costs all` で楽観・標準・悲観の3通りを並べられます。
**前提を変えて結論が反転するなら、それは優位性ではなくコスト仮定です。**

## 設計

### 層

```
    interfaces   →   application   →   core
   （CLI・組み立て）  （手続き）        （純粋関数）
                          ↑
                    infrastructure
                 （Port の実装を注入する）
```

`core` は他のどの層も import しません。`application` は自分が定義した Port にだけ
依存し、`infrastructure` を知りません。組み立ては `interfaces/composition.py`
だけが行います。この制約は `tests/test_architecture.py` が AST 解析で機械的に検査し、
層をまたぐ依存・core 内の `datetime.now()`・core への I/O ライブラリの侵入を検出すると落ちます。

**クリーンアーキテクチャは3層に留めています。** Entity/UseCase/Controller/Gateway の
5層に割るとファイル数が倍になり、研究段階の反復速度を殺すためです。
Port を切るのは「データ源を差し替える」「先読みの境界を1箇所に集める」という
実利のある2箇所だけに限定しています。

### FCIS（Functional Core, Imperative Shell）

| | Functional Core | Imperative Shell |
|---|---|---|
| 場所 | `core/**` | `application/**`, `infrastructure/**` |
| できること | 純粋関数、不変データ、計算 | ファイル・API・時刻・ログ |
| 禁止 | `datetime.now()`、I/O、乱数、引数の書き換え | 判断そのもの |

`core/contracts.py` の値オブジェクトはすべて `frozen=True` です。戦略に
`Portfolio` を渡しても、戦略側が中身を書き換えて会計を壊すことはできません。

これは設計の趣味ではなく実利です。**純粋であることが、ウォークフォワードの
再現性をタダで与えてくれます。** 同じ入力で必ず同じ結果になるので、
「パラメータを変えたのか、たまたまなのか」を切り分けられます。

### 先読みを構造的に不可能にする

この実装の中心はここだけです。他は必要になってから足します。

1日の処理順序を固定しています。

```
T日:
  1. 前日に出した注文を、T日の「始値」で約定させる
  2. T日の「終値」で建玉を評価し、資産曲線に1点打つ
  3. 戦略に「T日までのデータ」だけを渡し、注文を受け取る
  4. その注文は T+1日に持ち越す
```

**T日の引けで判断し、T+1日の寄りで約定する。** 同じ日の終値で約定させると
「終値を見てから買った」ことになり、成績が劇的に良くなります。
最も入りやすく、最も気づきにくい先読みです。

戦略が受け取る `MarketView` は `as_of` より後の行に**触れられません**。
規約ではなく、物理的にそうなっています。

ベクトル化（`shift`）ではなく1日ずつ回すのは、この保証のためです。遅くなりますが、
日次・500銘柄・10年（約125万バーイベント）で数十秒。研究段階では十分です。

### 先読み検出テスト

`tests/test_no_lookahead.py` のうち、最も強いのはこれです。

```python
def test_truncating_the_future_does_not_change_the_past():
    """期間を短く切っても、重なる部分の結果は完全に一致すること。"""
```

一致しないなら、どこかで未来を見ています。戦略を書き換えても効きます。
**このテストが落ちたら、他の全部の結果を捨ててください。**

### エンジンの配線チェック

合成データには `trend`（順張りが効く）と `meanrev`（効かない）の2種類を
仕込んであります。順張り戦略が前者で後者に勝つことを確認することで、
**売買の向き・損益の符号・約定タイミング**がまとめて検算できます。

## J-Quants の扱いで気をつける3点

### 0. 認証は API キー（V2 でトークン方式は廃止）

V1 の `/v1/token/auth_user` / `/v1/token/auth_refresh` は **削除されました**。
ダッシュボードの **[API Keys]** で発行したキーを `x-api-key` ヘッダーに載せます。
キー自体に有効期限はなく、再発行・削除で管理します。

あわせて V2 では次も変わっています。どれも例外にならず静かに失敗する種類です。

| | V1 | V2 |
|---|---|---|
| 認証 | refresh token → id token の2段 | `x-api-key` ヘッダー |
| レスポンス | エンドポイントごとのキー名 | 一律 `data` |
| 取引カレンダー | `/markets/trading_calendar` | `/markets/calendar` |
| 四本値の列 | `Open`/`Close`/`Volume` | `O`/`C`/`Vo` |

レスポンスのキーを間違えると `payload.get(key, [])` が空リストを返すだけなので、
**「その日はデータがなかった」として取り込みが素通りします**。
`tests/test_jquants_auth.py` と `tests/test_jquants_schema.py` で固定しています。

### 1. 銘柄一覧は必ず `date` 付きで取る

`/equities/master` は `date` を受け取り、**その日時点で上場していた銘柄**を返します。
省略すると今日上場している銘柄だけが返り、その期間に上場廃止になった銘柄が
母集団から消えます（**生存者バイアス**）。潰れた会社を除いた成績は当然良く出ます。

`scripts/fetch.py` は月次で `date` 付きで取得し、`data/raw/master/` に保存します。

### 2. 調整後価格は価格水準の判定に使えない

`/equities/bars/daily` は調整後（`AdjO`/`AdjC`…）と調整前（`O`/`C`…）、
そして調整係数 `AdjFactor` を返します。調整後は分割時に**遡及して書き換わります**。

- リターンの計算 → **調整後**（系列が飛ばない）
- 「株価1,000円以下」のような **水準の判定** → **調整前**

調整後で水準を判定すると、将来の分割を知っていることになります。
`tests/test_no_lookahead.py` でこれを固定しています。

### 3. 財務は `DiscDate` / `DiscTime` を使う

決算期末（`CurPerEn`）ではなく、TDnet で開示された日時です。
会計期間の終わりを基準にすると、まだ公表されていない数字で売買したことになります。
仕様にも「開示番号は順序を保証しない、開示日時で比較せよ」とあります。

### プランとレート制限

| プラン | 月額（税込） | 日足の遡及 | レート制限 | 2年分の取り込み |
|---|---|---|---|---|
| Free | ¥0 | 直近12週間を除く2年 | 5回/分 | 約98分 |
| Light | ¥1,650 | 5年 | 60回/分 | 約8分 |
| Standard | ¥3,300 | 10年 | 120回/分 | 約4分 |
| Premium | ¥16,500 | 20年 | 500回/分 | 約1分 |

Free の12週間遅延は「今日の値が取れない」だけで、**過去の再現には影響しません**。

**レート制限は V2 で明示されました。** Free の5回/分は12秒間隔です。
日付単位で2年分（約490営業日）を取ると最短でも98分かかります。
429 を受けてからバックオフする作りでは上限ぎりぎりで待ち時間が伸び続けるので、
`_RateLimiter` で**投げる前に**間隔を空けています。
取得済みの日付はスキップするので、途中で止めても再開できます。

`.env` の `JQUANTS_PLAN` は実際のプランに合わせてください。
速い値を入れると 429 を踏み続けます。

## 指標の読み方

`core/metrics.py` は数字と一緒に**警告**を返します。数字だけ見て判断しないためです。

もっとも信用してよいのは、勝率でも Sharpe でもなく

```
1取引あたり期待値 と、その標準誤差（t値）
```

です。期待値 +1.85%、標準誤差 2.15%、t = 0.86 なら、**優位性は「無い」と読むのが正しい**。
総リターンが +76% でもです。

自動で出る警告:

- 取引数が30件未満 → 勝率・PF は運の範囲
- |t| < 2 → 優位性があるとは言えない
- 日次リターンに自己相関 → √245 での年率換算が実態とずれる（Sharpe が過大）
- 粗利の30%超がコスト → 前提次第で結論が反転する水準
- 勝率が高いのに PF が低い → 小さく勝って大きく負ける形
- ベンチマークに勝っていない
- 約定しなかった注文が10%超

### ランダム比較（いちばん重要）

```bash
python scripts/run.py --compare --synthetic
```

同じ保有期間・同じ銘柄数でランダムに売買した場合の分布を出し、
戦略がその分布のどこにいるかを表示します。

```
戦略: sma_cross              +76.43%    +7.87%   -40.23%     0.47      68
買って持つだけ                 -2.57%    -0.35%   -41.90%     0.05       0
ランダム（中央値）            +52.58%                         0.49
ランダム（5-95%）          -33.85% 〜 +159.67%

戦略の Sharpe は、ランダム分布の 48 パーセンタイルです。
  → ランダムと区別がつきません。この戦略に優位性があるとは言えません。
```

**+76%でも、ランダムの分布の内側なら優位性ではありません。**
ほとんどの人がこの比較をやらないので、偶然を優位性と見誤ります。

95パーセンタイルを超えた場合も、**パラメータを何通り試したか**を思い出してください。
20通り試せば、偶然1つは95パーセンタイルに入ります（多重検定）。

### 新しい戦略を足すには

1. `strategies/` に `on_bar(view, portfolio) -> list[Order]` を持つクラスを書く
2. `strategies/__init__.py` の `REGISTRY` にファクトリとパラメータ格子を登録する

これだけで `run.py` も `validate.py` も最適化もそのまま使えます。
格子の組み合わせ数がそのまま試行回数 N になり、選択バイアスの大きさを決めるので、
**軸を1つ足すと N は掛け算で増える**ことを忘れないでください。

**DB は使いません。** 日足は全上場銘柄10年でも Parquet + pandas で足ります。
研究段階に RDB を入れると、スキーマ移行と ORM の都合が検証の速度を殺します。
SQL を投げたくなったら DuckDB から同じ Parquet を読めます。

**バックテストのライブラリも使っていません。** backtrader や vectorbt は
約定モデルを隠します。どこにバイアスが入るかを自分で把握することが目的なので、
最初は自分で書くほうが早いです。動くようになってから、同じデータで
`backtesting.py` と付き合わせて検算するのは有効です（食い違えばどちらかにバグがある）。

## Out-of-Sample 検証とウォークフォワード

```bash
# ホールドアウト（前7割で決めて、後3割で検証）
python scripts/validate.py holdout --strategy sma_cross --synthetic

# ウォークフォワード（本命）
python scripts/validate.py walkforward --strategy sma_cross --synthetic --train 250 --test 120

# 学習の窓を伸ばしていく方式
python scripts/validate.py walkforward --strategy sma_cross --synthetic --anchored
```

### なぜ分けるのか

同じ期間でパラメータを決めて同じ期間で成績を報告したら、その数字は
「最も都合のよい組み合わせを後から選んだ結果」でしかありません。

```
|--- 学習1 ---|-検証1-|
       |--- 学習2 ---|-検証2-|
              |--- 学習3 ---|-検証3-|

報告してよいのは 検証1 + 検証2 + 検証3 だけ
```

各窓の検証期間は**重なりません**（`validate_no_overlap` が保証）。重なると
同じ日を複数回成績に数えることになります。

`anchored=True` は学習の開始点を固定して窓を伸ばし、`False`（既定）は
学習の幅を固定してずらします。**両方回して結果が大きく違うなら、その戦略は
相場環境に強く依存している**という情報が得られます。

### 多重検定の補正

パラメータを N 通り試して一番良いものを選ぶと、その成績には
**「N回引いた中の最大値」という偏り**が必ず乗ります。真の優位性がゼロでも、
50回引けば見栄えのする1つは出ます。

真の Sharpe が 0 の戦略を N 個試したときの、観測される最大 Sharpe の期待値を
計算して比べます（Bailey & López de Prado）。

```
E[max SR] ≈ (1-γ)·Z⁻¹(1 - 1/N) + γ·Z⁻¹(1 - 1/(N·e))
```

この値を超えていなければ、**その結果は「何もない」と区別がつきません。**

```
【選択バイアス】
  各窓の格子        9 通り
  実際に比較できた数 4〜8 通り（取引数が足りない候補は除外）
  ! 2/14 の窓で、「優位性ゼロでも期待される水準」を超えていません
```

なお **探索に賢いアルゴリズムは使いません。** ベイズ最適化や遺伝的アルゴリズムは
「実質的に何通り試したか」が曖昧になり、この補正ができなくなります。
探索の賢さより、**何通り試したかを正直に数えること**のほうが検証の正しさには効きます。

### 何を最大化するか

既定は Sharpe です。総リターンを最大化すると、最もボラティリティの高い
パラメータが選ばれます（大きく賭ければリターンの期待最大値は上がる）。
`--objective total_return` は比較のために用意してあるだけで、既定にしてはいけません。

### 診断

```
【診断】
  判定              過学習が疑わしい
  学習の平均スコア  1.04
  検証の平均スコア  0.13
  劣化率            87%
  検証がプラスの窓  57%

【パラメータの安定性】
  fast          不安定  [40, 40, 10, 10, 25, ...] 変動係数0.46
  slow          安定    [50, 50, 50, 100, 75, ...] 変動係数0.29

【検証期間だけを繋いだ成績（報告してよいのはこれ）】
  総リターン        -34.09%
  最大ドローダウン  -50.96%
```

見るのは3つです。

1. **劣化率** — 学習から検証への落ち幅。半分くらいまでは正常（最良を選んでいるため）。
   7割以上落ちるなら過学習を強く疑う
2. **パラメータの安定性** — 窓ごとに 25/75 → 5/200 → 40/60 と変わるなら、その
   「最適値」はノイズです。実運用で次にどれを使うかも決められません
3. **検証がプラスの窓の割合** — 全体でプラスでも、1つの窓の大勝ちが全部を
   作っているなら再現性はありません

**判定は「有効」とは決して出しません。** 最良でも「否定はされていない」までです。
統計でできるのはそこまでで、それ以上書いた瞬間に嘘になります。

### 窓が足りないとき

J-Quants Free の2年（約490営業日）だと、学習250日・検証120日で**窓は2つ**しか
取れません。診断は `判定不能（データ不足）` を返します。目安は5窓以上なので、
まともなウォークフォワードには Light 以上（5年）が要ります。

## 意図的に作っていないもの

- 機械学習（単純なルールで優位性が出ないうちは、複雑にしても過学習が増えるだけ）

- 信用取引・空売り（現物のみ）
- 配当（トータルリターンで評価したくなったら足す）
- リアルタイム発注（検証が終わるまで不要）
